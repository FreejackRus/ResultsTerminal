# Установка и эксплуатация

## Целевые платформы

Терминал: Windows 10/11 x64, Ubuntu 24.04 x64, Astra Linux SE 1.8 x64. Шлюз: Linux-служба Node.js 24 LTS с SQLite. Полная матрица фактических проверок — в `verification.md`.

Ubuntu/Astra требуют WebKitGTK 4.1. Linux-сборка выполняется на Debian 12, а установка и оборудование проверяются на целевой ОС. На Astra использовать доверенные репозитории учреждения; не отключать мандатный контроль и не подключать сторонние репозитории ради обхода ошибки.

## Шлюз

1. Создайте отдельного непривилегированного пользователя `results-terminal`. Разверните исходники/пакет в `/opt/results-terminal` и установите Node.js 24 LTS и pnpm 11.25.0.
2. Выполните `pnpm install --frozen-lockfile` и `pnpm build`. Либо используйте gateway tarball с уже собранной панелью; для него нужны установленные зависимости из lockfile, но повторная сборка панели не требуется.
3. Создайте `/etc/results-terminal/gateway.env` по `deploy/gateway.env.example`, права 0600. Укажите пути к действительному TLS-сертификату и ключу, доступные сервисному пользователю. Приватный ключ не помещать в репозиторий.
4. Задайте случайный `RT_SETUP_TOKEN` длиной от 24 символов, передайте его администратору защищённым способом. Демонстрационные значения не использовать.
5. Установите `deploy/results-terminal-gateway.service` в `/etc/systemd/system/`, выполните `systemctl daemon-reload` и `systemctl enable --now results-terminal-gateway`.
6. Откройте `https://<адрес>:8787/admin/`, создайте администратора и настройте МИС. После создания администратора удалите `RT_SETUP_TOKEN` из environment-файла и перезапустите службу.
7. Зарегистрируйте терминалы. Сеть и firewall должны разрешать только необходимые направления: терминал → шлюз, администратор → шлюз, шлюз → МИС.

Шлюз в production запускается через `pnpm start:gateway`; отсутствие TLS блокирует запуск. `pnpm dev` запускает только loopback HTTP и синтетическую МИС и не предназначен для внешнего доступа.

Для восстановления сохраняйте SQLite, соответствующий `.key` и настройки TLS/службы. Делайте резервную копию с остановленной службой либо штатным SQLite backup; не копируйте только активный DB-файл, забыв WAL. `.key` нельзя терять или заменять — это сделает сохранённый ключ МИС нечитаемым. После рестарта пациентские сессии не восстанавливаются.

## Терминал Windows

Нужны Windows WebView2 и установленный драйвер принтера. Установите NSIS-пакет, SumatraPDF из официального дистрибутива и настройте системную очередь. SumatraPDF не поставляется внутри приложения. В панели укажите имя принтера и при необходимости полный путь helper.

В первом запуске введите HTTPS-адрес шлюза и одноразовый код. Сертификат шлюза должен быть доверенным для ОС. Учётная запись киоска должна иметь ограниченный доступ к файловой системе и настройкам ОС. Приложение не изменяет политики безопасности Windows.

## Терминал Ubuntu / Astra

Установите DEB из артефактов сборки, зависимости WebKitGTK и `cups-client`, настройте CUPS и тестовую очередь. Для serial-сканера предоставьте пользователю доступ к конкретному порту через штатную группу/udev-политику. Не используйте `chmod 777` и запуск приложения от root.

Для автозапуска можно установить `deploy/results-terminal.desktop` в пользовательский `~/.config/autostart/`; настройка киоск-сессии и ограничение выхода средствами ОС выполняются администратором учреждения.

## Разработка нативной части

Запустите `pnpm dev`, чтобы работали шлюз, демо и браузерный Vite. В другом терминале:

```sh
pnpm --filter @rt/terminal exec tauri dev --config '{"build":{"beforeDevCommand":""}}'
```

JSON-кавычки зависят от shell; альтернативно остановите frontend Vite и используйте стандартный `tauri dev`, запустив шлюз/демо отдельными процессами. Физическую печать проводить только на разрешённом тестовом принтере.

## Сборка поставки

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm --filter @rt/terminal tauri build --bundles nsis --ci
# На Debian 12:
pnpm --filter @rt/terminal tauri build --bundles deb --ci
pnpm package:gateway
```

Артефакты Tauri — в `apps/terminal/src-tauri/target/release/bundle/`. Gateway tarball — `dist/resultsterminal-gateway-0.1.0.tar.gz`. Подписание Windows-пакета требует сертификата владельца; неподписанный пакет не выдаётся за подписанный.

CI проверяет код, browser demo и собирает Windows NSIS и Debian 12 DEB. Workflow `astra-build.yml` запускает официальный контейнер Astra UBI 1.8 на GitHub-hosted Ubuntu runner: отдельная машина для сборки не требуется. Образ берётся из официального registry; если требуется авторизация, задайте GitHub Secrets `ASTRA_REGISTRY_USERNAME` и `ASTRA_REGISTRY_PASSWORD`. После сборки выполняются установка DEB, проверка библиотек и headless smoke-test от непривилегированного пользователя. Первый успешный запуск: https://github.com/FreejackRus/ResultsTerminal/actions/runs/40179582343 . Для новой версии откройте Actions → Astra 1.8 package on GitHub → Run workflow; пакет находится в артефакте `terminal-astra-1.8-x64`.

Отдельный `astra-acceptance.yml` остаётся для выделенного self-hosted стенда Astra 1.8: он нужен для проверки полноценной ОС и оборудования. Сборка в UBI-контейнере не подтверждает работу ядра/СЗИ и принтера/сканера на установленной Astra. Сведения о доступности образа: https://registry.astralinux.ru/download/ .

## Приёмка оборудования

На каждой целевой ОС проверить установку, запуск, подключение к шлюзу, реальный скан каждого поддерживаемого типа, отображение PDF и выдачу тестового документа на разрешённом принтере. Затем отключить сканер и принтер, остановить очередь, потерять сеть и убедиться, что мониторинг не показывает устаревшее состояние как исправное. Записать ОС, версии драйверов, модели устройств, SHA сборки и результаты. Состояние очереди не заменяет проверку лотка.
