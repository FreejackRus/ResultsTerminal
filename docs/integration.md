# Интеграция МИС

## Роли и версии

Учреждение реализует HTTPS API `/integration/v1`. Шлюз инициирует запросы; МИС ищет пациента, подтверждает право доступа, выдаёт результаты и преобразует внутренние форматы в готовый PDF. Терминал не подключается к базам МИС и сетевым папкам.

Контракт находится в `openapi/integration.json`, генерируется `pnpm openapi` из общих схем. Версия API — `1`, media type JSON — `application/json`. Авторизация сервиса — `Authorization: Bearer <key>`; ключ известен только шлюзу и МИС. Для DELETE без тела не посылайте JSON Content-Type.

## Последовательность

1. `GET /integration/v1/capabilities` → `{ "apiVersion": "1", "methods": ["oms-birth", "order-code"] }`.
2. `POST /integration/v1/identifications` → `{ "method": "order-code", "identifier": "000001", "proof": "246810" }`.
3. После проверки МИС возвращает `{ "sessionId": "opaque-session", "expiresAt": "...ISO 8601...", "patient": { "displayName": "ФИО для экрана" } }`.
4. `GET /integration/v1/sessions/{sessionId}/results` → `{ "items": [...], "nextCursor": null }`.
5. Следующие страницы запрашиваются с `?cursor=...`; курсор непрозрачный, до 200 символов. Максимум 100 результатов в странице; ID уникальны в сессии.
6. `GET /integration/v1/sessions/{sessionId}/results/{resultId}/pdf` → PDF-байты с Content-Type `application/pdf`, не redirect, не URL и не путь к файлу. До 25 МиБ.
7. `DELETE /integration/v1/sessions/{sessionId}` → 204. Последующие запросы закрытой/истёкшей сессии → 410.

Сессия МИС должна истекать самостоятельно, даже если шлюз потерял сеть и не смог отправить DELETE. Шлюз ограничивает свою сессию 15 минутами и всегда проверяет принадлежность терминалу. Во внешнем API шлюза идентификаторы сессии и документов заменяются собственными непрозрачными ID.

## Способы идентификации

| method | identifier | proof / подтверждение |
| --- | --- | --- |
| `oms-birth` | ОМС строкой | Дата рождения YYYY-MM-DD |
| `oms-name` | ОМС строкой | ФИО; учреждение включает этот способ явно |
| `barcode` | Выданный МИС секретный токен | Не требуется отдельное поле |
| `qr` | Выданный МИС секретный токен | Не требуется отдельное поле |
| `order-code` | Номер заказа | Отдельный код доступа |
| `contract-code` | Номер договора | Отдельный код доступа |
| `patient-code` | ID пациента | Отдельный код доступа |
| `phone-otp` | Телефон | Через challenge |

Обычный публичный номер заказа/результата не является безопасным токеном. МИС должна проверять право выдачи документов и не включать в capabilities неподдерживаемые способы. Идентификаторы не преобразуются в числа — ведущие нули значимы.

Для телефона первый запрос возвращает `{ "challengeId": "opaque", "expiresAt": "..." }`. МИС отправляет OTP собственным способом. `POST /integration/v1/identifications/confirm` получает `{ "challengeId": "...", "code": "123456" }` и возвращает сессию. Код и факт его выдачи не передаются через диагностические API. Срок challenge шлюза — не более 2 минут, максимум 5 попыток; МИС также ограничивает свои попытки.

## Результаты

```json
{
  "items": [{
    "id": "opaque-result",
    "title": "Клинический анализ крови",
    "date": "2026-10-24",
    "category": "Лабораторные исследования",
    "status": "ready",
    "pdfAvailable": true
  }],
  "nextCursor": null
}
```

`status` — `ready` или `pending`. Неготовый документ не выдаётся. Пустой список — нормальный ответ 200 с `items: []`, а не серверная ошибка.

## Ошибки

Формат: `{ "error": { "code": "SESSION_EXPIRED", "correlationId": "..." } }`. Не включать ФИО, полис, токены, содержимое документа, пути и stack trace. 400 — валидация, 401/403 — отказ доступа, 404 — документ отсутствует, 410 — сессия истекла, 429 — ограничение частоты, 503 — МИС недоступна. Шлюз возвращает `INVALID_MIS_RESPONSE` при нарушении схемы/типа PDF. Запросы не повторяются автоматически после неопределённого внешнего действия.

## Проверка реализации

`pnpm contract:check` запускает локальную демо-МИС и проверяет все восемь объявленных способов, пагинацию, сигнатуру PDF и отказ после завершения сессии.

Для внешней МИС задайте `RT_MIS_URL`, `RT_MIS_KEY`, при необходимости `RT_MIS_CA` (путь к PEM) и `RT_CONTRACT_FIXTURES` (локальный JSON с разрешёнными синтетическими данными). Fixture — объект с ключами method и соответствующим телом идентификации; для `phone-otp` добавьте поле `otp`. Файл не коммитить. Пример структуры — `examples/contract-fixtures.json`.

Внешняя проверка требует HTTPS и не должна выполняться на реальных пациентах. Результат PASS означает совместимость проверенных сценариев, а не готовность конкретного медицинского внедрения.
